# 2026-08-11 심사 리뷰 지적 12건 조치 계획

리뷰 원문: BE P0 4건 + P1 2건 + P2 1건, AI P0 2건 + P1 3건.
조사 근거는 이 문서 각 항목의 "확인된 사실"에 요약한다(전수 조사는 세션 산출물).

## 0. 범위 결정

| 항목 | 결정 |

| BE-P2 (실운영 RBAC) | **범위 밖**. 공유 Bearer + 읽기 전용 플래그는 캠프 데모의 의도된 경계다. 대신 P0-2에서 결정 주체를 **자기신고 값으로 정직하게 기록**해 감사 기반만 놓는다. |

## 1. 확정된 설계 결정 (조사로 뒤집힌 것 포함)

### D1. 결정 주체(actor)의 정직한 기록
FE `lib/operator.ts`는 `NEXT_PUBLIC_` 표시용 이름(기본 "홍길동")이고 인증은 공유 Bearer 하나뿐이라,
서버가 토큰에서 담당자를 도출할 수 없다. `actor_id`를 검증된 신원처럼 저장하면 감사 기록이 형식만 남는다.
→ 요청에서 받되 **자기신고임을 함께 저장**한다: `decided_by: {actor_id, actor_name, auth: "shared_token", verified: false}`.
RBAC 도입 시 `auth`/`verified`만 바뀐다.

### D2. 에러 코드 등급 (계약 §8 L792/L796 동시 개정)
기존 계약은 구조가 같은 조건부 필수 필드 누락(`selected_rate`)을 400으로 못 박았다.
새 필드만 422로 두면 같은 성격의 위반이 코드에 따라 갈린다.
→ **422 = 조건부 필수 필드 누락**, **400 = 값이 있으나 유효하지 않음**으로 등급을 가르고 `selected_rate` 누락도 422로 옮긴다.
검사 순서: `404` → `400`(decision enum) → `409`(상태 전이) → `422`(조건부 필수) → `400`(값 범위).
FastAPI 네이티브 422는 `detail`이 배열이라 계약 머리말(`{"detail": "문자열"}`)과 FE 파서(`api.ts:107`)를 깬다
→ `RequestValidationError` 핸들러로 단일 문자열 정규화.

### D3. `version` 낙관적 잠금은 선택 필드
필수로 하면 결정 API 호출 19곳이 전부 깨지고 FE는 애초에 `Card.version`을 읽지 않는다.
→ 보내면 조건부 쓰기에 포함, 없으면 기존 `status=pending` 조건만. FE는 배선한다.

### D4. `candidate_store_id`는 `CAND-00N`이 **아니다**
`candidates.json`의 `id`는 점포 식별자가 아니라 **순위 슬롯**이다(재실행 실증: 후보가 가맹 전환되면
CAND-001이 다른 점포를 가리킨다). 절대 규칙 6상 소진공 상가(진단)와 하이원 가맹점(처방)의 ID도 분리해야 한다.
→ `p8_sensitivity.identity()` 선례를 따라 안정 키 `{eup} {category} {name}@{lat:.6f},{lng:.6f}`를 쓴다.
**BE가 카드 생성 시 계산**하므로 파이프라인 수정이 필요 없다.

### D5. `verified_merchant_id`의 원천은 `FRCS_REG_NO`
`merchants.json`에는 ID가 없지만 커밋된 원응답 캐시 `data/raw/api_cache/merchants_raw.json`에
1,682행 전부 유일한 `FRCS_REG_NO`가 살아 있다(결측 0·중복 0). `strip_pii`가 떨구지 않는 필드다.
→ `p3_merchants.py` main() 루프에 `merchant_id` 한 항목 추가. name+address 해시를 새로 만들 필요 없다.

### D6. 쿨다운은 EXPANSION 전용
INCENTIVE는 `target`이 없어 "같은 대상 재제안" 개념이 성립하지 않고, pending 1장 제한 때문에
반려가 유일한 재생성 경로다(테스트 5곳이 이 패턴에 의존). 리뷰 지적 사례도 EXPANSION이다.
기본 90일, 요청에서 조정 가능(0~365).

### D7. 진행 기록 `unit`은 입력받지 않고 서버가 채운다
FE `progressMetrics.ts`가 "%와 %p를 틀리면 실제와 5배 다른 값"이라고 못 박은 정본을 갖고 있다.
사용자가 단위를 자유 입력하면 그 오류가 되살아난다.
→ `measured_from`/`measured_to`/`source`/`scope`는 입력 필수, `unit`과 `is_proxy`는 **서버가 지표 정의에서 채워 저장**한다.
감사 기록에 단위가 남아야 한다는 요구는 충족되고 오입력 경로는 닫힌다.

### D8. 완료는 빠른 상태 변경으로 만들 수 없다
`POST /progress`(quick_status)는 `metrics: {}`를 보내므로 증빙을 실을 자리가 없다.
완료는 위젯 배지·KPI에 직결되므로 증빙 없이 만들어지면 안 된다.
→ quick 경로의 `완료`는 422로 막고 `progress-records`로 유도한다.

### D9. INCENTIVE도 비교문·근거를 서버가 재생성한다
지금 INCENTIVE는 `comparison`·`reasons`·`expected_effect`가 LLM 원문 그대로 저장되고,
인용한 %p가 서버 `SCENARIOS`와 일치하는지 확인하는 코드가 **전혀 없다**. AI-P0-1의 진짜 구멍이 여기다.
→ EXPANSION과 같은 구조로 서버 템플릿 재생성, LLM은 비정량 리스크만. `confidence`도 LLM 자기평가를
쓰지 않고 서버 고정("중")으로 바꾼다 — 그러지 않으면 P0-2의 저신뢰 승인 게이트가 LLM 자기신고에 좌우된다.

### D10. AI 스키마는 EXPANSION/INCENTIVE로 분리
지금 두 호출이 같은 `CARD_AI_SCHEMA`를 공유해 INCENTIVE가 쓰지도 않는 `ai_rank_target`·`dissent`를
강제 생성하고 서버가 버린다. 후보 ID 기반 근거 검증을 얹으려면 분리가 전제다.
`evidence_ids`는 enum이 아니라 `string` + **서버 화이트리스트 대조**로 한다(요청마다 바뀌는 enum은
매 호출이 새 스키마가 되어 12초 예산을 갉아먹는다).

### 4-1. 적대적 교차 검토에서 나온 조치 (최종 121 passed)
