# 18. 프론트엔드 리디자인 변경 기록

> 대상 브랜치: `FE-design` · 비교 기준: `main`(`742d780 prototype`)
> 규모: **53개 파일 · +2,322 / −749**, 커밋 10개
> 이 문서는 "무엇을 왜 바꿨는가"의 기록이다. **무엇을 그리는가**의 정본은 13(디자인 가이드),
> **무엇을 고칠 것인가**의 계획은 17(FE 디자인 실행 계획)이다. 이 문서는 17의 결과 보고에 해당한다.

---

## 0. 한 줄 요약

화면은 이미 다 만들어져 있었고 부족한 것은 **편집**이었다(17 §2). 그래서 기능을 더하지 않고
**색 체계·정보 위계·화면 분업**을 손봤다. 가장 큰 변화 셋은 다음과 같다.

1. **테마 전환** — 웜 크림 + 인디고 + 다크 사이드바 → 쿨 화이트 + 라벤더 + 라이트 사이드바
2. **허브 재편** — 4막이 세로로 쌓이던 화면을 마스터-디테일(좌 미리보기 / 우 작업 목록)로
3. **상세 분리** — `/proposals/[id]` 라우트 신설, 근거·전망·결정을 여기로 이관

## 1. 색 체계 — 웜에서 쿨로

토큰 값 자체가 바뀌었기 때문에 개별 컴포넌트를 고치지 않아도 화면 전체가 따라왔다.

| 토큰 | `main` | 현재 | 비고 |
|---|---|---|---|
| `admin.bg` (페이지) | `#f4f1e9` 웜 크림 | `#FAFAFB` 쿨 니어화이트 | |
| `admin.surface` (카드) | `#fffdf8` 웜 오프화이트 | `#FFFFFF` 순백 | |
| `admin.primary` (강조) | `#5146d8` 인디고 | `#8B7BF0` lavender-500 | 유일한 채움색 |
| `admin.sidebar` (사이드바 면) | `#17113b` 딥 네이비 | `#FAFAFA`* | *별도 토큰 `sidebar-surface`로 분리 |
| `admin.border` | `#ded8ca` 웜 베이지 | `#E7E5EE` 쿨 그레이 | |

**왜**: 크림 배경에 인디고 강조는 따뜻하고 부드럽지만, 공공기관 의사결정 도구에서
"정확한 수치를 읽는 화면"이라는 인상을 주기 어려웠다. 배경을 중립 쿨톤으로 낮추면
숫자와 라벤더 강조가 더 또렷하게 떠오른다.

**폰트**도 함께 바로잡았다. `main`의 스택은 `-apple-system` → … → `Pretendard` 순서라
**Mac에서는 Pretendard가 한 번도 적용되지 않았다**(SF Pro가 먼저 잡힘). Pretendard를 맨 앞으로
올려 개발자·심사위원 화면에서 같은 글꼴이 보이게 했다.

## 2. 사이드바 — 어두운 면에서 밝은 면으로

| | `main` | 현재 |
|---|---|---|
| 배경 | `#17113b` 딥 네이비 | `#FAFAFA` + 우측 0.5px `#E7E5EE` 실선 |
| 글자 | `text-white` / `white/50` | `#2B2833` / `#55525F` |
| 항목 정렬 | "추진 기록 입력"만 `lg:ml-3` 들여쓰기 | 예외 없음 — 아이콘 20px·간격 12px·패딩 12px 통일 |
| 하위 메뉴 | 항상 표시 | 그 작업 영역(`/tracking*`) 안에서만, 연결선으로 |
| 활성 강조 | 항목이 각자 판정 | 상위에서 한 번 판정 → 경로당 정확히 1개 |
| 로고 | 라벤더 칩 안 마크 + 옆에 텍스트 | 조합형 로고 하나 |

**왜**: 히어로와 본문이 이미 밝은 면이라 사이드바만 어두우면 화면이 두 덩어리로 갈렸다.
정렬은 "추진 기록 입력"만 이유 없이 밀려 보여 세로로 훑을 때 아이콘 열이 끊겼다 —
하위 관계는 들여쓰기가 아니라 **부모 아이콘 중심에서 내려오는 연결선**으로 표현했다.
들여쓰기만 있으면 정렬 오류로 읽히지만 선이 있으면 소속으로 읽힌다.

**대비 검증**: 배경을 밝히면서 12px 보조문의 대비가 떨어져, 사이드바 보조 텍스트를
`admin.text-muted`(#6E6C7A)에서 `admin.text-soft`(#55525F)로 한 단 올렸다.
현재 값 — 메뉴 제목 13.8:1 · 부제·그룹 제목 7.3:1 · 활성 항목 5.2:1 (모두 WCAG AA 통과).

## 3. 허브(`/`) — 4막 세로 쌓기에서 마스터-디테일로

### 이전

```
[다크 라벤더 배너: 인사말 + 종류 필터 + 생성 버튼]
[KPI 카드 4장]
[히어로 8 / 사이드 4]
━━ 02 근거 ━━  추이 차트 + 업종·정량 순위
━━ 03 전망 ━━  페이백 3·5·7% 시나리오
━━ 04 실행 ━━  나머지 결정 대기 · 최근 결정 · 실행 현황 · 6스텝
```

### 현재

```
[문서 머리말: 인사말 + 생성 버튼]                    ← 다크 배너 제거
[sticky 상태 바: 2 결정 대기 · 1 실행 관리 · 0 완료 · ▸이번 분기 진단]
━━ 01 결정 ━━
  ┌ 좌 60% 미리보기 ──────┬ 우 40% 작업 목록 ───┐
  │ 선택된 카드 요약·근거   │ 결정 대기 N건        │
  │ [근거·전망 검토하기 →]  │ 실행 관리 N건        │
  │                       │ 이번 분기 완료 N건    │
  │                       │ 데이터 원천          │
━━ 02 점검 ━━  결정 이력 · 실행 현황 · 6스텝
```

**바꾼 이유와 근거**

**① 근거·전망 막을 상세로 옮겼다.** 허브의 02·03막은 `/dashboard`와 `/incentive`를 통째로
복제하고 있었다(17 §3.2). 담당자가 허브에서 답해야 할 질문은 "오늘 무엇을 결정하나" 하나인데,
분석 화면을 그대로 얹어 놓아 폰에서 10화면 길이가 됐다.

**② 상태 바를 만들고 진단 지표를 접었다.** 분기 진단 4지표는 파이프라인 배치로 **분기에 한 번**
바뀌는 배경 맥락인데 매일 보는 화면의 최상단을 차지하고 있었다. 매일 바뀌는 값(몇 건 남았나)이
그 자리로 올라오고, 진단은 토글 뒤 압축 뷰로 내려갔다. 상태 바는 `sticky`라 스크롤 내내 붙어 있다.

**③ 마스터-디테일로 바꿨다.** 대기 건을 비교하려면 상세로 들어갔다 나오기를 반복해야 했다.
이제 목록 줄을 누르면 페이지가 아니라 좌측 미리보기가 갈린다(`?selected=`). 상세로 가는 길은
좌측 카드의 버튼 하나뿐이다.

**④ 숫자와 목록의 단위를 맞췄다(결함 수정).** 이전에는 "결정 대기 2건"을 누르면 **카드 한 장짜리
상세**가 열렸고, 화면 어디에도 2건 전체 목록이 없었다. 지금은 상태 바의 숫자와 목록의 줄 수가
**같은 배열의 길이**라 정의상 어긋날 수 없다. 종류 필터 3스코프에서 검증했다.

**⑤ 최상단 종류 필터를 걷어냈다.** 카드가 2건뿐이라 과잉이었고, 이 필터의 "전체 2"가 바로 아래
상태 바의 "2 결정 대기"와 나란히 놓여 **세는 축이 다른 두 숫자**로 읽혔다(종류별 vs 상태별).
컴포넌트는 지우지 않고 대기 목록 헤더로 옮길 자리를 주석에 남겼다.

**⑥ 인사말에 담당자 이름을 넣었다.** 사이드바에 하드코딩돼 있던 이름을 `lib/operator.ts`
한 곳으로 모으고(환경변수 → 데모 시드 → 역할 이름 폴백), 히어로와 사이드바가 같은 출처를 본다.

## 4. 제안 상세(`/proposals/[id]`) — 신규 라우트

허브에서 뺀 근거·전망이 여기로 왔다. 위에서 아래로 **요약 → 근거 → 전망 → 변경 이력**이고,
**결정 바만 하단 고정**이다.

**왜 결정 바를 고정했나**: 이전에는 승인·반려·보류 버튼이 3,800px 스크롤 맨 아래에 있었다.
AI 제안이 확정되는 유일한 지점(절대 규칙 4)이 화면에서 가장 찾기 어려운 자리에 있으면 안 된다.
승인=그린 / 반려=레드 / 보류=앰버로 상태색을 유지했고 라벤더는 쓰지 않았다.

**요약 헤더는 카드 종류로 갈린다.** 확충은 지표 3개(지역 근거·현재 비중·순위 안정도)와
원 Score 병기, 인센티브는 3·5·7% 시나리오와 가정 기반 전망 고지를 싣는다. 인센티브에는
대상 지점이 없으므로(전 지역 공통) 읍×업종·지도 자리를 억지로 만들지 않는다 —
이전에는 인센티브 카드에도 "지역 근거: 6개 지역 공통 / 현재 비중: 정량 비교 필요" 같은
빈 지표가 떴다.

기존 `/cards/[id]`(지도·후보 정밀 검토·적격성)는 그대로 두고 근거 막에서 링크로 잇는다.

## 5. 카드 표현 — 테두리에서 배경 대비 + 그림자로

| | `main` | 현재 |
|---|---|---|
| 카드 | `border border-admin-border` + `shadow-card` | 테두리 없음 + `shadow-card` |
| `shadow-card` | `0 8px 24px / 0.06` (넓게 퍼짐) | `0 1px 3px / 0.04` + `0 1px 2px / 0.03` |

**왜**: 선과 그림자를 둘 다 쓰면 경계가 두 번 그려져 화면이 딱딱해진다. 배경(#FAFAFB)과
표면(#FFFFFF)의 밝기 차가 이미 있으므로 그림자는 접촉면만 남기고 최소화했다.

**예외 두 곳** — 배경 대비가 일할 수 없는 자리에서는 다른 장치를 썼다.

- **흰 패널 안의 카드**(6스텝 스트립): 부모가 이미 흰 면이라 표면을 올릴 수 없어
  방향을 뒤집어 낮은 면(`#F5F4F8`)을 썼다.
- **지역별 현재 상태 6카드**: 카드 안에 11px 보조문이 빽빽해 면을 낮추면 대비가
  4.15:1로 AA에 못 미친다. 여기서만 1px 실선을 남겼다. 입력·버튼의 테두리를
  남겨 둔 것과 같은 기준(조작 가능성·경계는 선이 맡는다).

## 6. 지역별 현재 상태 — 무지개 색 띠 제거

`main`은 6개 지역 카드 상단에 지역마다 다른 색 띠를 그렸다
(`absolute inset-x-0 top-0 h-1` + `REGION_COLORS[region]`).

**문제**: 그 색은 **아무것도 인코딩하지 않았다.** 배정에 규칙이 없고 단순히 6개를 다르게 칠한
장식이었는데, 화면에서 가장 시끄러운 요소라 정작 의미 있는 신호인 **`진단 대상` 라벤더 배지를
덮고** 있었다. 13 §4의 "색은 신호일 때만"에 어긋난다.

**조치**: 색 띠를 걷고 **진단 대상 2곳(영월군·삼척시)만** 옅은 라벤더 면 + 라벤더 실선으로
표시했다. 지역 구분은 지역명·진단 순위·수치가 이미 하고 있다.

추이 차트의 지역별 선 색은 **유지**했다 — 거기서는 색이 곧 어느 지역인지를 가리키는 기능색이다.
업종 도넛의 6색도 같은 이유로 유지했다.

## 7. 브랜드 로고 교체

| | `main` | 현재 |
|---|---|---|
| 파일 | `sangseng-navigator-mark.svg` (마크만, 1KB) | `sangseng-navigator-lockup.png` (조합형, 720×140) |
| 표시 | 라벤더 칩 안 마크 36/44px + 옆에 "상생 나침반" 텍스트 | 로고 하나 (데스크톱 216×42 · 모바일 180×35) |

**왜 주변 요소를 걷어냈나**: 새 로고가 마크와 워드마크를 함께 담은 조합형이라, 옆에 두던
"상생 나침반" 텍스트는 브랜드명을 두 번 쓰는 셈이 됐다. 라벤더-500 칩도 뺐다 —
로고 마크가 자체 인디고를 갖고 있어 칩 위에 얹으면 두 보라가 부딪힌다.
`지역상생 Decision OS` 부제도 함께 정리했다.

**배경 투명 처리**: 받은 원본은 배경이 불투명 `#F8F8F8`이었다. 현재 사이드바(`#FAFAFA`)와는
2/255 차이라 당장은 티가 안 나지만 사이드바 색을 조정하면 회색 사각형이 드러난다.
그래서 배경을 키잉해 알파로 빼냈다(완전 투명 66% · 안티앨리어싱 가장자리 1.5% 보존).
배경 위에 합성된 색을 원래 전경색으로 되돌리는 방식이라 글자에 흰 테가 생기지 않는다.
용량도 101KB → 56KB로 줄었다.

**크기 규칙**: 원본 비율이 720:140 = **36:7**이므로 표시 크기는 이 비율의 정수배만 쓴다
(216×42 · 180×35 · 144×28). 다른 값을 쓰면 글자가 눌린다.

로딩 스켈레톤도 같은 로고를 쓴다 — 자리표시 사각형을 두면 스켈레톤에서 실화면으로
넘어갈 때 브랜드가 한 번 깜빡인다.

## 8. 용어 정리 — 개발자 어휘에서 실무 어휘로

**표시 텍스트만** 바꿨다. 변수명·타입·API 필드·HTML id(`#decision-queue` 등)는 그대로 두었다.

| 이전 | 현재 |
|---|---|
| 데모 표본 | 예시 데이터 |
| 가용 후보 선택 | 선택 가능한 후보 |
| 활성 업무 제외 후 선택 | 진행 중인 건 제외하고 선택 |
| AI 순위 조정 | AI가 순위 반영 |
| Work Item | 업무 항목 |
| 활성 업무 | 진행 중인 업무 |
| 큐 / 결정 대기 큐 | 목록 / 대기 목록 |

`#decision-queue` 같은 식별자는 화면에 뜨지 않으므로 손대지 않았고,
"비비큐"·"바베큐" 같은 실제 가맹점 상호도 제외했다.

> ⚠ **이 치환은 `frontend/`에서만 끝났다.** 같은 문장이 백엔드
> `services/cardgen.py`의 `_grounded_ai()`에도 있어서, **실 API 모드에서는 옛 용어가
> 그대로 보인다**(§11 후속 과제). 03 문서 §1의 영역 분리 규칙에 따라 이 브랜치에서는
> 손대지 않았다.

## 9. 지킨 것 — 정직성 장치 (절대 규칙)

리디자인 내내 아래는 제거·축소하지 않았다. 매 라운드 렌더된 HTML로 확인했다.

| 장치 | 근거 | 현재 상태 |
|---|---|---|
| `근사 지표` 배지 | 절대 규칙 2 | 전환율 수치가 보이는 자리와 **1:1**. 진단이 접히면 수치도 함께 감춰지고, 펴면 배지가 반드시 함께 나온다 |
| `가정 기반 전망` 배지·고지 | 절대 규칙 3 | 시뮬레이션·페이백 시나리오 출력 블록마다 유지 |
| 원 Score 순위 병기 | 절대 규칙 5 | `정량 Score N위 → 선택 가능한 후보 M위` 그대로. 허브 미리보기에는 텍스트 요약(`원 Score 상위: …`)으로 병기 |
| AI는 제안만 | 절대 규칙 4 | 결정 바를 오히려 더 찾기 쉬운 자리(하단 고정)로 올렸다 |
| Gini·HHI 미노출 | 절대 규칙 1 | `npm run check:banned` 통과 |
| 상태색 분리 | 13 §4 | 승인=그린 / 반려=레드 / 보류=앰버, 증감은 `trend.*`. 라벤더로 칠하지 않았다 |

## 10. 검증

각 변경마다 아래를 돌렸다.

```bash
cd frontend
npm run check:banned     # 금칙어 (지니·Gini·HHI·실행하겠습니다)
npm run build            # 타입 + 프로덕션 빌드
```

추가로 렌더된 HTML을 직접 파싱해 확인한 것들:

- **상태 바 숫자 = 목록 줄 수**: 3블록 × 종류 필터 3스코프 = 9조합 전부 일치
- **활성 메뉴 1개**: 6개 경로에서 사이드바 `aria-current="page"`가 정확히 하나
- **큐 클릭이 페이지 이동을 하지 않음**: 대기 목록 안 `<a href>` 0개 / `<button>` 2개
- **정직성 장치 잔존**: 근사 지표·가정 기반 전망·원 Score 병기 카운트
- **대비비**: 사이드바·카드 텍스트를 WCAG 기준으로 계산해 AA 미달 시 색을 한 단 진하게 조정

## 11. 남은 것

- **백엔드 용어 치환이 필요하다 (유탁 담당 · 우선).** `services/cardgen.py`의 `_grounded_ai()`가
  만드는 카드 비교문에 `활성 업무`·`가용 후보`가 남아 있다. 이 문장은 상위 후보가 제외된 상황에서
  LLM 출력을 덮어쓰고 화면에 그대로 실리므로, **실 API 모드에서는 §8의 용어 정리가 반쪽**이다.
  mock(`cards.json`·`store.ts`)은 이미 바뀌어 있어 두 모드의 문구도 갈린 상태다
  (03 문서가 요구하는 `store.ts` ↔ `cardgen.py` 1:1 대응이 지금은 깨져 있다).
  적용할 치환은 아래 2줄뿐이다.

  ```diff
  - f"정량 상위 후보 {', '.join(skipped)}는 활성 업무가 있어 중복 제안에서 제외했습니다. "
  - f"따라서 가용 후보 중 최고점인 정량 {target['rank']}위 {target['eup']} "
  + f"정량 상위 후보 {', '.join(skipped)}는 진행 중인 업무가 있어 중복 제안에서 제외했습니다. "
  + f"따라서 선택 가능한 후보 중 최고점인 정량 {target['rank']}위 {target['eup']} "
  ```

- **`/cards/[id]`와 `/proposals/[id]`가 공존한다.** 둘 다 "이 제안을 승인할 근거가 되나"에
  답하는 화면이라 담당자 입장에서는 상세가 둘인 셈이다. 역할을 명확히 가르거나(결정용 / 실행 후
  정밀 검토용) 합치는 판단이 필요하다.
- **`/dashboard`(491줄)는 이번 범위 밖**이라 흰 카드가 길게 이어지는 구조가 남아 있다.
  17 §4.2의 3막 재편이 아직 반영되지 않았다.
- **`sampleQuality` 세 상태의 어투가 섞여 있다** — `예시 데이터` / `표본 보강 필요` / `운영 표본`.
  용어 정리 범위가 첫 번째만이라 나머지 둘은 그대로 두었다.
- **`전체 비중 %`가 `lavender-500`이라 대비가 3.4:1**이다. 18px 굵은 글씨라 큰 텍스트 기준(3:1)은
  넘지만 여유가 없다. `lavender-700`으로 내리면 6.5:1이 되고 색감 차이는 거의 없다.
